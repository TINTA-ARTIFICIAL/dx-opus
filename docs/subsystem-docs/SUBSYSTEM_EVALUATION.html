01 — Propósito

Qué hace el subsistema Evaluation

Evaluation es el subsistema que valida la calidad de los artefactos producidos por el sistema antes de que el editor tome decisiones sobre ellos. Evalúa investigación, textos y contenido derivado — y lo hace siempre con el mismo formato de resultado, independientemente del tipo de artefacto que esté analizando.

La decisión de diseño central del subsistema es la separación entre el contrato de evaluación y la lógica de cada evaluador. Los workflows que invocan evaluadores solo necesitan saber que recibirán un resultado con un estado (GREEN, YELLOW o RED) y una orientación de decisión. Cómo se llega a ese estado — qué dimensiones se evalúan, con qué pesos, con qué umbrales — es responsabilidad exclusiva de cada evaluador y puede cambiar sin que los workflows se vean afectados.

Evaluation no decide si el proyecto continúa o se detiene. Señala y orienta — el editor juzga y decide. Un resultado RED no significa que el proyecto muera: significa que hay trabajo que hacer antes de avanzar.

Qué no hace Evaluation

  • →No define el Perfil Editorial del editor — eso es Editorial Profile. Solo lo consume como input para evaluar adherencia de estilo.
  • →No define la jerarquía de fuentes ni el Validation Checklist — eso es Knowledge Base. Solo los consume para evaluar calidad de investigación.
  • →No produce texto ni investigación. Solo evalúa artefactos producidos por otros subsistemas.
  • →No es el último paso del proceso. La evaluación puede invocarse en cualquier punto — no solo al final.

Dónde interviene en el sistema

Research · Fase 5

EVALUATE_RESEARCH_REPORT
Valida la calidad de la investigación antes de pasar a escritura. Obligatorio antes de invocar cualquier prompt de Writing.
Writing Book · Fase 5

Dos evaluaciones independientes: rigor de fuentes y claims en el texto, y adherencia a la voz del editor. Ambas obligatorias antes de cerrar el libro.
Writing Post · Fase 3

Valida voz, estructura y calidad editorial antes de publicar. Produce orientación específica de mejora si el resultado no es GREEN.
02 — Conceptos clave

El modelo conceptual

Evaluation opera sobre dos pilares: el contrato de evaluación, que define el formato estable de cualquier resultado, y los evaluadores individuales, que contienen la lógica específica de cada tipo de artefacto.

El contrato de evaluación

Todo evaluador del sistema produce exactamente el mismo formato de resultado. Este formato — el EVALUATION_RESULT — es el contrato estable que permite a los workflows consumir evaluaciones sin conocer la lógica interna de cada evaluador.

EVALUATION_RESULT — formato canónico
status
GREEN | YELLOW | RED — resultado principal. Es lo primero que lee el editor.
score
X / 100 — puntuación ponderada. Complementa el status; no lo sustituye.
decision_guidance
Qué debe hacer el editor a continuación. Orientación concreta, no genérica.
blocking_issues
Solo presente en RED. Lista de problemas que impiden avanzar hasta resolverse.
improvement_areas
Presente en YELLOW. Áreas específicas a reforzar antes de continuar.
strengths
Presente siempre. Lo que funciona bien y debe preservarse en iteraciones.

El semáforo — qué significa cada estado

GREEN
LISTO PARA AVANZAR
El artefacto cumple los criterios de calidad. El editor puede continuar al siguiente paso del workflow directamente. No se requiere iteración.
YELLOW
NECESITA REFINAMIENTO
El artefacto es aceptable pero tiene áreas mejorables. El editor decide si reforzar las áreas señaladas antes de continuar o avanzar asumiendo las limitaciones identificadas.
RED
REQUIERE REWORK
El artefacto tiene problemas que bloquean el avance. El editor debe resolver los blocking_issues antes de continuar. No es un resultado definitivo — es una señal de trabajo pendiente.

Los evaluadores activos

Cada evaluador tiene su propia lógica interna — dimensiones, pesos, umbrales — pero todos producen el mismo EVALUATION_RESULT. La lógica interna puede evolucionar entre versiones sin afectar a los workflows que los invocan.

El principio de ownership

Todos los evaluadores del sistema son propiedad del subsistema Evaluation, independientemente de qué inputs necesiten para funcionar. Esto incluye EVALUATE_BOOK_STYLE, que necesita el Perfil Editorial como input pero pertenece a Evaluation porque su función es evaluar — no modelar al autor.

El criterio es funcional, no de dependencia: lo que determina el ownership es qué hace el artefacto, no qué consume. Este principio garantiza que todos los evaluadores se desarrollan con coherencia bajo una única responsabilidad — el subsistema Evaluation — y que pueden evolucionar juntos cuando el contrato de evaluación se actualice.

03 — Guía de uso

Cómo leer e interpretar un resultado

El editor no interactúa directamente con Evaluation — los workflows lo invocan en los momentos adecuados. Lo que el editor hace es leer el EVALUATION_RESULT y decidir qué hacer con él. Esta sección explica cómo hacerlo.

Orden de lectura de un resultado

PasoQué leerPara qué
1statusDetermina inmediatamente si se puede avanzar (GREEN), si hay decisión pendiente (YELLOW) o si hay trabajo obligatorio antes de continuar (RED).
2decision_guidanceIndica qué acción concreta debe tomar el editor. Es la instrucción operativa del resultado.
3blocking_issues o improvement_areasSolo en RED o YELLOW respectivamente. Lista los problemas o áreas específicas que requieren atención.
4strengthsPresente siempre. Identifica qué funciona bien para que el editor no lo modifique en iteraciones.
5scoreLectura opcional. El score complementa el status pero no lo determina — un texto puede tener score 72/100 y status YELLOW o GREEN según la distribución de las dimensiones.

Qué hacer con cada status

  • GREEN Avanzar al siguiente paso del workflow. No es necesario iterar ni corregir, aunque el editor puede hacer ajustes menores si lo desea. Los strengths identificados son una referencia útil para mantener el nivel en los artefactos siguientes.
  • YELLOW El editor lee las improvement_areas y decide. Puede optar por reforzar antes de continuar (recomendado si las áreas son relevantes para el texto final) o avanzar asumiendo las limitaciones (aceptable si el editor considera que las áreas señaladas no son críticas para su objetivo).
  • RED El editor lee los blocking_issues y trabaja en resolverlos antes de continuar. Según el evaluador, la resolución puede implicar volver a fases anteriores del workflow — por ejemplo, un RED en EVALUATE_RESEARCH_REPORT puede requerir añadir fuentes (Fase 0) y repetir la investigación profunda (Fase 4).

En EVALUATE_BOOK_STYLE, la violación de cualquier NO-GO del Perfil Editorial produce un RED automático independientemente del score total. Un NO-GO no es una preferencia — es una restricción que el editor ha definido explícitamente como incompatible con su voz.

Cuándo invocar la evaluación fuera del flujo estándar

Los evaluadores no están limitados a los checkpoints que definen los workflows. El editor puede invocarlos en cualquier momento:

  • →Antes de publicar un texto externo al sistema — EVALUATE_BOOK_STYLE puede usarse para evaluar un capítulo escrito manualmente por el editor y verificar su coherencia con el perfil antes de incorporarlo al libro.
  • →Durante la escritura de un libro largo — si el editor sospecha que el estilo se está desviando en los capítulos intermedios, puede invocar EVALUATE_BOOK_STYLE en mitad del proceso para corregir antes de que el problema se acumule.
  • →Sobre investigaciones de proyectos anteriores — EVALUATE_RESEARCH_REPORT puede aplicarse a un research report existente para verificar si sigue siendo válido antes de usarlo como base de un texto nuevo.
