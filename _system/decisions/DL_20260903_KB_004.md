# DECISION LOG ENTRY: DL_20260903_KB_004

## DECISION

Diseño de gobernanza para la propagación de `RESOURCE_SOURCE_AUTHORITY` (SAH) y `RESOURCE_CLAIM_VALIDATION` (CVC) desde las copias por-proyecto (en `R_research/`) de vuelta a la base de conocimiento global del editor (`D-X-OPUS/resources/`) — issue #70. Responde a las tres preguntas de diseño planteadas en ese issue:

1. **¿Automática o aprobada por el editor?** → **Aprobada por el editor.** Nunca automática.
2. **¿La maneja `PROMPT_UPDATE_VALIDATION_CHECKLIST` directamente?** → **No.** Ese prompt aplica el `CANONICAL UPDATE SCHEMA` de SAH/CVC (procedimientos A–D) dentro del alcance del proyecto — es un paso distinto, con distinto radio de impacto, de la propagación al entorno global del editor.
3. **¿Herramienta dedicada?** → **Sí, un paso explícito separado**, no un efecto colateral de otro workflow. En el sistema actual (Apps Script/Drive) sería un `TOOL_UPDATE_KNOWLEDGE_BASE` nuevo; en la arquitectura de plugin (`DL_20260903_SYSTEM_041`, `SPEC_PLUGIN_ARCHITECTURE.md`) es la acción de actualización de la skill `knowledge-base`, protegida por el mismo hook de gobernanza ya diseñado ahí.

**Esta entrada es solo de diseño — no implementación.** Ver bloqueo en IMPLEMENTATION PRIORITY.

## RATIONALE

Propagar una copia por-proyecto a `D-X-OPUS/resources/` cambia el punto de partida de **todos los proyectos futuros** del editor — un radio de impacto muy distinto al de una actualización dentro de un solo proyecto. `RESOURCE_SOURCE_AUTHORITY` ya define en su `CANONICAL UPDATE SCHEMA` (v2.1) que los cambios de schema "deben ser aprobados por KB-dev y comunicados via DL entry" — extender ese mismo principio de aprobación explícita a la propagación cross-proyecto es una generalización directa del criterio que el propio documento ya aplica, no una regla nueva inventada aquí.

Automatizar la propagación, o dejarla como efecto colateral silencioso de `PROMPT_UPDATE_VALIDATION_CHECKLIST`, reproduciría la misma clase de riesgo que el bug #66 (modificación no autorizada de un artefacto compartido) — la razón por la que `SPEC_PLUGIN_ARCHITECTURE.md` §5.1 ya decidió promover Knowledge Base a skill propia con hook de gobernanza en vez de contenido embebido.

## AFFECTED SUBSYSTEMS

- **KNOWLEDGE_BASE**: define el contrato de qué constituye una propagación válida (mismo `CANONICAL UPDATE SCHEMA` que ya rige ediciones dentro del proyecto)
- **RESEARCH**: `PROMPT_UPDATE_VALIDATION_CHECKLIST` no cambia de alcance — sigue operando solo dentro del proyecto
- **SYSTEM**: la herramienta/acción de propagación es responsabilidad de SYSTEM (Apps Script hoy) o de la skill `knowledge-base` del plugin (Sprint 6+)

La propagación necesita localizar de forma fiable la copia por-proyecto de SAH/CVC en `R_research/`, y ese es exactamente el bug de resolución de carpetas que #49 (S5-03 del backlog Sprint 5) todavía no se ha corregido. No implementar nada de esta DL hasta que S5-03 esté cerrado.

Una vez desbloqueada, la implementación real converge con Sprint 6+ (plugin): en vez de construir un `TOOL_UPDATE_KNOWLEDGE_BASE` de Apps Script de vida corta, tiene más sentido implementar esto directamente como la acción de actualización de la skill `knowledge-base`.
